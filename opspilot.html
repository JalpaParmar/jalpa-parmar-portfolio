02

Problem

Support requests often need interpretation before engineering can act. Someone has to summarize the issue, identify impact, decide where it belongs, suggest validation, establish ownership and follow progress.

That creates repetitive coordination work and inconsistent handoffs. I created TriagePilot to explore which parts could be assisted by AI and automation while keeping important decisions with people.

03

My Approach

I started with the handoff and the decisions people need to make. I kept the first version small so I could test that workflow before considering integrations.

Stakeholder needs

These roles are modeled for the portfolio scenario; they are not a record of stakeholder interviews.

Support Team
Clear ownership and progress visibility.
Engineering
Useful technical context instead of raw customer text.
QA
Clear validation scenarios.
Product
Visibility into recurring product issues.
Technical Project Manager
Ownership, blockers, priorities and delivery visibility.
Engineering Leadership
High-impact issues and workload visibility.

MVP scope

In scope

  • Support queue and structured triage
  • Summary, category and priority suggestions
  • Validation ideas and routing recommendations
  • Human approval and engineering work tracking
  • Status visibility and operations digest
  • Recommendation feedback

Out of scope / future

  • Real integrations, production LLM and customer data
  • Authentication / RBAC and production database
  • Automated customer communication
  • Automated release decisions
  • SLA prediction

I treated priority and routing as recommendations because customer impact and ownership still need human judgment. The reviewer can change the summary, priority, queue or engineer, or return the request for more information.

04

Workflow & Architecture

In the demo, context review and routing confirmation happen in the same review form. Approval is the final action that creates engineering work. People retain escalation and release decisions.

Technical view

Support Platform → Integration / Normalization → Analysis Engine → Human Review → Work Management → Status / Reporting

For the portfolio demo, I kept the implementation intentionally simple: static web technology, synthetic data and deterministic rules. A production implementation would require secure integrations, authentication, persistent storage, audit logging and evaluated model access.

Try the handoff: open SUP-101, review or edit its suggestions, approve it, change the engineering status and check the digest.

Handoff quality

Routing override rate

The demo shows feedback from synthetic session decisions. Acceptance alone does not establish accuracy, and I do not claim business improvements from this prototype.

07

What I Learned / Next Step

The useful part of this exercise was deciding where automation helps and where a person still needs to make the call. Making review explicit also made the requirements and validation scenarios clearer.

If I took this beyond a portfolio prototype, my next step would be to validate the workflow with support and engineering users before connecting an external system or production AI model.
